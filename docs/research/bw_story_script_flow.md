# 黑白原版如何控制剧情与剧情战斗

这份笔记记录《宝可梦 黑/白》Field Script（地图脚本）的剧情控制方式，以及我们服务端剧情层如何对应实现。结论来自对用户自有 ROM 的反汇编与抽取结果，仅用于本地个人研究。

## 一句话结论

原版没有一个叫“剧情”的对象，也没有“必打战斗”这种引擎概念。剧情就是**地图上的脚本**：NPC 对话、踩格子、进出门、地图初始化都会跳到一小段字节码。字节码用 flag 和 work（变量）做条件跳转；战斗是脚本里的三条指令（设置训练家 → 开始对战 → 取回结果），结果写进一个 work，紧接着的条件跳转决定接下来放哪段台词、下一步去哪。

## 数据放在哪里

| 数据 | NARC | 说明 |
| --- | --- | --- |
| 地图脚本文件 | `a/0/5/7` | 每个文件 = 偏移表 + 16 位指令流 |
| 剧情文本 | `a/0/0/3` | XOR 加密的字符串表，`0xF000` 控制换行与 `{name}` 等替换 |
| 区域头 | `a/0/1/2` | field 4 = 脚本文件号，field 6 = 文本文件号 |
| NPC 实体 | `a/1/2/5` | 每个 NPC 带一个 16 位 `script` id |
| 全局脚本表 | overlay 10 + `0x15206` | `script` id ≥ 1000 的入口（见下文） |

诺文镇卧室（我们的 `unova_in_391`）在区域头里是 **脚本文件 782 / 文本文件 430**。脚本文件开头是相对偏移表：每项 4 字节，值相对“表项之后的位置”，以 `0xFD13` 结束；NPC 的 `script` id 是这张表里 1-based 的序号。卧室开场那段脚本在文件内的字节范围约为 `539..1912`。

## 脚本 VM 用到的指令

这些是本次反汇编里实际出现、且被 `tools/rom/extract_dialogues.py` 的 VM 实现的指令（编号与参数宽度见 `tools/rom/bw_script_ops.json`，语义按公开的 Gen 5 脚本文档）：

- `0x02`：脚本结束。
- `0x08` / `0x09`：压入常量 / 压入变量值；`0x0A`：弹栈写入 work。
- `0x10`：读 flag；`0x23`–`0x25`：设置/清除 flag。
- `0x19` / `0x1A`：比较 work 与立即数 / 两个 work，结果存进“上一次比较结果”。
- `0x1F`：**条件跳转**。1 字节条件 + 4 字节相对偏移；条件命中就跳到偏移处，否则继续。这是剧情的“if”。
- `0x3D`：播放一段文本（参数是文本文件里的编号），等玩家按键。
- `0x85`：设置训练家（3 个 u16 参数：训练家编号 + 战斗参数）。
- `0x8E`：开始对战（无参数，用上一条 `0x85` 设置好的训练家）。
- `0x8D`：把战斗结果写进一个 work（参数是 work 编号）。

flag 是 1 位的剧情开关（NPC 是否出现、门是否锁），work 是 16 位变量（选了什么御三家、战斗胜负）。两者都是存档的一部分。

## 卧室开场脚本的实际流程

把 782 号脚本里卧室那段按指令读出来，顺序是：

1. 一串 `0x3D` 文本：Cheren 催开礼物盒、Bianca 惊叹、三人各自拿到宝可梦。
2. 选择御三家。脚本把玩家的选择写进 work **`0x4030`**：`0` = Tepig，`1` = Oshawott，`2` = Snivy。
3. Bianca 提议对战，Cheren 反对，Bianca 坚持（文本 37/38 一带）。
4. `0x85` 设置训练家 + `0x8E` 开打 + `0x8D 0x8010` 取回结果。
   - 训练家编号按 `0x4030` 分支：**59 = Bianca 带 Oshawott，60 = Snivy，61 = Tepig**，都是 Lv.5。她永远拿克制玩家选择的那只。
   - `0x8010` 里 `1` = 玩家赢，`0` = 玩家输。
5. `0x1F` 条件跳转：赢 → 文本 46（“It's amazing that you won…”），输 → 文本 44（“{name}'s Pokémon needs to be fixed up, too.”）。两条分支在治疗前合流。
6. Cheren 治疗双方（脚本里的治疗指令），Bianca 提议让 Cheren 也打一场。
7. 第二场：`0x85` + `0x8E` + `0x8D 0x8010`。
   - 训练家编号：**53 = Cheren 带 Tepig，54 = Oshawott，55 = Snivy**，都是 Lv.5。Cheren 永远拿和玩家相同的那只。
8. 再次按 `0x8010` 分支（胜负台词分别是文本 55/56），然后文本 57（“Oh! I'd better come, too!”），脚本结束。

这段脚本没有“战斗必须打赢”的判断：输了也走 `0x8010 == 0` 的分支，治疗完继续第二场。所谓“必经”，是因为整个开场由同一个 NPC 脚本驱动，脚本没跑完之前房间的门/楼梯不会给你下一步。

`server/content/rom/npc_dialogues.json` 里区域 391 的 NPC 2（Bianca）能直接看到这台词的完整顺序——抽取器的 VM 不执行 `0x85/0x8E`，所以战斗和分支被“摊平”成了一条直线；这也反过来证明战斗指令就在这段脚本中间，而不是另挂在地图事件上。

## 其他剧情点的控制方式

- **NPC 对话**：NPC 实体带 `script` id，交互时执行对应脚本。脚本里用 flag/work 判断进度，播不同文本；结束时可能设置 flag。
- **踩格子触发**：地图事件里的 trigger 也指向脚本，例如第一次走出小镇、进入某条道路。
- **进出门/传送**：warp 事件指向脚本或坐标；脚本可以再 `warp` 玩家。
- **地图初始化**：区域头里有一段 init 脚本，进图时执行（我们对应 `onEnter`）。
- **拦路**：原版常用“NPC 站在路口 + 脚本条件”或直接改通行权限；剧情推进后 NPC 移开或脚本放行。

## 全局脚本表（`script` id ≥ 1000）

区域头里的 `script` id（以及 NPC 实体上的 `script`）都是**全局**的，小于 1000 的由区域自己的脚本文件按序号解析，≥ 1000 的要先查一张常驻表。这张表在 overlay 10 的文件偏移 `0x15206`（运行时 RAM `0x216a386`），每项 10 字节、5 个 `u16`：`start`、`end`、`scriptFileId`、`msgArcId`、`msgFileNo`。条目按 `start` 从大到小排列，解析规则是“第一个 `start <= id` 的条目命中”，脚本在文件里的序号是 `id - start`。

从 ROM 里能稳定读出 15 条记录（`10424` 一路降到 `10250`，之后字节流开始错位，末尾还能按 10 字节重新对齐到 `2200 / 2100 / 2000`）。按 `msgFileNo` 解密对应的文本库，内容是真实引擎功能，而不是残留数据：文本库 9 是地铁对战（Battle Subway），261 是电梯楼层播报，281 是图鉴评价员，313 是宝可传送实验室，159 是通用的路人 NPC 台词，另有 464 / 348 / 315 / 282 / 421 / 284 / 367 / 10 等一批。这些文本已经抽进 `.tools/global_scripts.json`（仅本地，已 gitignore）。

**`scriptFileId` 的复核结论（2026-10-27）**：它确实是字段脚本归档 `a/0/5/7`（899 个成员）的成员下标，但大多数成员是 4–24 字节的单脚本桩：`366`–`375` 每个只有一条脚本，`1131`/`1132` 超出归档范围；只有 `632` 是真实脚本（4 条，引用文本库 261 的电梯楼层文本）。因此多数 range 的行为不在字节码里，而是原生代码。原文“一个也没能执行到文本”只对桩成员成立，对 `632` 不成立。

把 1134 个全局 id 按 NPC 实际使用拆开：只有 **30 个 NPC** 落在已解码的 `10250–10424` 范围内，且全是服务设施（神秘礼物 14、地铁 8、宝可传送 4、梦境碎片/交换/个体值鉴定各 1）；其余是 355 个共用 `2000` 对象脚本、341 个训练家脚本（`type 1`，属于训练家数据）、348 个 `5000–10249` 环境/对象脚本、27 个 `2100/2101`、7 个 `2200–2282`、26 个高于表范围。所以全局表不是剧情导入的阻塞项，而是服务设施清单；逐项目录见 `server/content/rom/global_script_catalog.json`。

结论：全局表的结构和文本库已经确定；它能覆盖的 30 个 NPC 都是服务设施，不是剧情。剧情 NPC 走的是区域局部脚本（1123 个 NPC，969 个已解码档案），序章用的是 782 / 文本 430。全局表影响的是电梯、售货机、神秘礼物这类通用交互，应按 handler 实现，不需要为它补全字节码映射。

## 我们的对应实现

| ROM | 本项目 |
| --- | --- |
| 脚本 VM + `0x1F` 条件跳转 | `StoryController` 的 step 列表 + step 上的 `when` |
| flag / work | `CharacterState.storyFlags`（按玩家保存） |
| `0x3D` 文本 | `say` step（台词来自 ROM 文本抽取） |
| `0x4030` 御三家编号 | `chooseStarter` 选项的 `value`，写入 `prologue.starter` |
| `0x85` + `0x8E` | `battle` step（`trainer` 或 `variants`） |
| `0x8D 0x8010` | `battle.resultFlag`（1 胜 / 0 负） |
| `0x1F` 按胜负分支 | `when: {"8010": 1}` / `{"8010": 0}` 的台词 step |
| 训练家表（53–55、59–61） | `nuvema.json` 的 `trainers` + 按 `prologue.starter` 选 `variants` |
| 脚本跑完才放行 | 场景结束才写 `prologue.bedroomDone`，两个对手的 `visibleWhen` 才变 |

客户端不需要知道这些：它只负责把 `say` 页翻完、把 `battle` 打完，然后发 `battle_closed` 告诉服务端“结算框关掉了”，剧情才继续。

## 复现方式

```bash
python tools/rom/extract_dialogues.py --rom "<你的 ROM>" \
  --out ../server/content/rom/npc_dialogues.json
python tools/rom/extract_dialogues.py --check      # 只校验已有输出，不写文件
```

脚本不依赖 ndspy：ROM 的文件名表被裁剪过，脚本/文本/区域头三个 NARC 都由 `tools/rom/nds_fs.py` 按内容识别（脚本归档 899 个成员、文本归档 472 个、区域头 427 条记录）。全局脚本表的审计写到 `--global-out`（默认 `.tools/global_scripts.json`）；因为里面是 ROM 文本，默认不进仓库。

输出里按 zone 记录 `scriptFile` / `textFile` 和每个 NPC 的台词。要看到 `0x85/0x8E/0x8D` 本身，需要按 `bw_script_ops.json` 的参数宽度把 782 号脚本从偏移表起点线性反汇编；`extract_dialogues.py` 的 `run_script()` 已经实现了除战斗三条以外的全部控制流，可以当作反汇编器的基础。
