# 原版如何驱动地图角色的移动与朝向

这份笔记回答一个问题：**《黑/白》原版里，NPC 走路、转向、被剧情控制，是同一套机制还是三套？** 结论用于修掉“NPC 倒着走”“楼梯不渲染”这类看起来像美术 bug、实际是数据管线 bug 的问题，并说明移植层应该对齐哪些规则、哪些细节不必复刻。结论来自对用户自有 ROM 的反汇编与像素级检查，仅用于本地个人研究。

## 一句话结论

移动和朝向在引擎里是**同一件事**：脚本给对象下发一串“动作”，每个动作自带方向和步数（“向左走一格”“向上转”），引擎照着播，播完才继续脚本。**方向从不根据坐标差推断**——所以原版里不可能出现“倒着走”。我们出现的倒走，是精灵表把左右两个方向的帧号写反了，和移动逻辑无关。

## 数据放在哪里

| 数据 | NARC / 位置 | 说明 |
| --- | --- | --- |
| 地图脚本 | `a/0/5/7`（FAT 299） | 卧室 391 = 脚本文件 782 |
| 移动动作表 | **脚本文件内部**，代码段之后 | 不是独立档案，`0x64` 用指针指过去 |
| NPC 实体 | `a/1/2/5` | 每个对象带 `faceDirection` 和 `movement` 字节 |
| 行走图 | `a/0/4/9` + 对象码表 `a/0/4/8` | 32×32 的 4×N 帧图集 |
| 室内物件 | **未命名的 FAT 472**（64 个 AB 包） | 户外用 `a/2/2/9`（FAT 471，52 个包）；`a/2/2/8` 是 FAT 470，只有 6 个包，是干扰项 |

## 脚本层：applymovement 与 waitmovement

卧室脚本里两条指令承担全部演出：

- `0x64` **applymovement**：参数 `<u16 对象 id> <u32 指针>`，指针**相对“本条指令结束处”**，即目标 = `pc + 8 + 指针`。
- `0x65` **waitmovement**：无参数。脚本在这里停住，等对象把动作播完才继续。

实测（脚本文件 782，14 个入口）：`0x64` 出现 18 次，**18 次指针都精确落在以 `FE 00 00 00` 结尾的动作块上**；其中 14 次后面紧跟 `0x65`。同样的解码在 zone 390（780）和 396（792）上一致：32/26、17/10。这三点合起来说明：对象移动是“下发—等待”的阻塞模型，不是引擎按坐标插值。

对象 id 的取值也印证了这一点：`0x0000`、`0x0001` 是实体表里的 0 号、1 号对象，`0x00FF` 表示**玩家自己**。

## 移动字节码：每 4 字节一个动作

动作块是定长记录，没有文件头、没有长度字段，靠终止符结束：

```
u16 动作 id | u16 重复次数        … 直到 FE 00 00 00
```

脚本 782 里能直接读到的两段（十六进制）：

```
0x074c  0F 0F  0C 0C 0C 0C  0F  45        // 走 2 格、走 4 格、走 1 格、结束
0x0760  3F 3F  0F 0F 0F  0C 0C  0F  45    // 停 2 拍、走 3 格、走 2 格、走 1 格、结束
```

同表里还有 `0x07ac/0x07b4/0x07bc/0x07c4` 四段只有单个动作的块：`20`、`21`、`22`、`23`——这就是“原地转身”用的四个方向动作。脚本要某个 NPC 转向时，下发的是一段长度为 1 的移动序列，而不是设置一个朝向字段。

常用动作 id（本次实测 + 公开的 Gen 5 movement 文档）：

| id | 含义 |
| --- | --- |
| `0x0C`–`0x0F` | 四个方向的行走（方向语义见下面的“未解决”一节） |
| `0x20`–`0x23` | 四个方向的原地转身 |
| `0x3F` | 停顿（次数 = 拍数） |
| `0x45` | 结束并让对象消失 |
| `0x4B` / `0x4C` | 头顶表情（感叹号等） |
| `0x4E` / `0x4F` | 跳跃 |

**未解决**：`0x0C`–`0x0F` 具体对应哪个方向，没有在本 ROM 里独立验证成功。把两段序列放到卧室的可走格上做穷举，24 种映射里有 10 种都能走通（房间开口太多，可走性区分度不够），所以之前“只有一种映射成立”的说法不可靠，已撤回。这个语义我们**不需要**：移植层用坐标差推方向，对正交单格步进是等价的。

## 精灵表的方向布局（像素级验证）

行走图是 32×32 的帧序列，按家族命名。用“肤色像素的水平重心相对图心的偏移”给每一帧判朝向（左 `/` 右 `/` 正面）、用“有没有脸”判正/背面，13 张已抽取的表 + 主角表全部可判读：

| 家族 | 帧数 | 上 | 下 | 左 | 右 |
| --- | --- | --- | --- | --- | --- |
| `t4x4cycle` | 16 | 0–2 | 3–5 | **6–8** | **9–11** |
| `t4x4x14` | 14 | 0–2 | 3–5 | **6–8** | **9–11** |
| `t4x4x20` | 20 | 0–2 | 3–5 | **6–8** | **9–11** |
| `t4x4nflip` | 12 | 0–2 | 3–5 | **6–8** | **9–11** |
| `t4x4flip` | 7 | 0–1 | 2–3 | 4–6 | **镜像 4–6** |
| `t4x4pcwoman` | 9 | 0–1 | 2–3 | 4–6 | **镜像 4–6** |
| 主角（`nuvema/actors/hero`） | 32 | 1–3 | 4–6 | 7–9 | 10–12 |

量化证据（肤色重心偏移，正数=朝右）：Cheren `npc_12` 的 7/8/9 号帧分别是 −0.22/−0.20/−0.25，10/11/12 号帧是 +0.22/+0.20/+0.25；Bianca `npc_135` 同样 ±0.21；主角 7–9 号 −0.20/−0.16/−0.26，10–12 号 +0.20/+0.16/+0.26。**左在前、右在后**，三种不同家族、三个人物完全一致。

“flip” 家族（7 帧）只画了一侧，另一侧在游戏里靠镜像；`t4x4pcwoman`（9 帧）同理，最后两帧是同方向的补帧。这两类表如果照 12 帧表的规则取帧，右侧会拿到左侧的画面——和本次的“倒着走”是同一种错。

## 室内物件：两个 prop 档案不能混用

室内房间的物件不是地图模型的一部分，是**摆件**：区块（`a/0/0/8`）里带一张摆放表，每条记录给出世界坐标、旋转和物件 id，物件本体在 AB 包里。AB 包分两套：

- `a/2/2/9`（FAT 471）：52 个包，户外物件，包 6 里有 `pc_01 / gate_01 / rock_01 / fountain_01 / o_chair_01`。
- **未命名的 FAT 472**（文件名表在这里就断了，只能按内容找）：64 个包，室内家具，包 53 里有 `tv01 / stair_u01 / stair_d01 / table01 / chair01 / shelf01–06 / bed01 / sink01 / ref01 / plant01 / win01 / pcdesk01 / desk01`。
- `a/2/2/8` 是 FAT 470，只有 6 个包，和室内家具无关——按路径名猜会猜错，这就是当初要按内容识别的原因。

**两个档案是两套 id 空间**：在同一个档案内部，任何 id 在所有包里都指向同一个物件（64 个包全量统计 0 冲突，52 个包同样 0 冲突）；跨档案则有 138 个 id 撞号——室内 `2 = tv01`，户外 `2 = t2_house01`，户外 `6 = t1_labo_01`。所以“拿户外档案解析室内房间”不是缺模型，而是把房子、栅栏、球场摆进卧室；这也是 `library.json` 里出现 `buill_02 / o_chair_01 / searock_01` 的原因。

贴图同理：FAT 418（52 个，户外）、FAT 419（64 个，室内），和 AB 包一一对应。

卧室 391 的区域记录 `area=212`，`area[1]=212` 是贴图集，包号是 `212 // 4 = 53`。**这个公式只在诺文那几间房成立**：拿全部 270 个有家具的房间去对，`area[1] // 4` 只能让其中四分之一把物件解析全（178 个房间会是空的），所以真正的规则是“先按覆盖选包、再用贴图集打平”，而且**包只是贴图分组、不是可用性边界**：同一个 id 在任何一个包里的模型字节完全相同（室内 144 个 id、户外 291 个，0 个 id 有两个模型），所以房间里的物件可以从各自需要的包里取，只有整个档案都没有的 id 才算真缺（全部 3355 个物件实例里只有 46 个，集中在 23 个其实是户外地图的 zone）。规则见 `tools/rom/prop_resolve.py`。区块 505 在这间房里摆了三个物件：

| 物件 id | 名字 | 世界坐标 | 格 |
| --- | --- | --- | --- |
| `0x0002` | `tv01` | (−200, 0, −216) | (3, 2) |
| `0x0004` | `stair_d01` | (−96, 0, −216) | **(9, 2)** |
| `0x0013` | `plant01` | (−88, 0, −184) | (10, 4) |

三个 id 在 FAT 472 的包 53 里全部命中；在 FAT 471 里一个都没有——因为 FAT 471 只有 52 个包，索引 53 越界，旧代码在这种情况下**静默回退到 `area[0]`（=6，诺文镇户外包）**，于是电视、楼梯、植物换成公园椅子一样解析不出来，随后被第二处静默 `continue` 丢掉。`library.json` 里 `zone_391` 的 `props` 因此是空数组——**楼梯不是没做，是被丢了**。

楼梯格 (9, 2) 在权限表里是实心（`behavior 1 / flags 0x0081`），原版把 warp 放在它前面的接触带 (8, 2)，所以我们地图里的 portal 位置是对的；缺的只是那块看得见的楼梯模型。

## 我们的实现 vs 原版

| 环节 | 原版 | 移植层现状 | 影响 |
| --- | --- | --- | --- |
| 行走指令 | `0x64` 指定对象 + 动作序列，`0x65` 阻塞等待 | `walk` step（`npcId` + `path`），服务端按 `path.length × msPerTile` 定时 | 基本等价；`path` 由人写，写错不会报错 |
| 方向来源 | 动作自带 | `path` 每跳由服务端带上 `dir`（`directionBetween`），客户端只照着播；`walk` 校验每跳相邻、允许原地转身 | 已对齐；斜跳/跨格在内容校验阶段就会报错，不再静默 |
| 转向 | 单独的转身动作（`0x20`–`0x23`），脚本可随时下发 | 已有独立 `face` step（`npc_face` 消息），`facing: "player"` 按实时格子算方向 | 已对齐；`walk` 结束也会定格朝向，可带 `vanish` 复刻 `0x45` |
| 行走图方向 | 左 6–8、右 9–11 | `extract_overworld_sprites.direction_layout()` 已按家族给号（左 6–8、右 9–11） | 已修；抽帧时用肤色重心自检，左右写反直接报错 |
| flip 家族 | 右侧镜像左侧 | 7/9 帧表额外写出镜像帧并在 `actor.json` 里指向它们 | 已修；`audit_assets.py --sprites` 会复查 |
| 室内物件 | 室内 AB 包（FAT 472 / 419），按覆盖选包 | 旧管线读了户外包（FAT 471 / 418），越界回退到 `area[0]` | 楼梯、电视、植物、多数家具缺失；房间里还混进房子和球场 |

## 修复清单

1. `tools/rom/extract_unova_indoor.py` + `tools/rom/prop_resolve.py`：按内容识别 AB 包档案和贴图档案（不再靠路径名猜）；每个场景按“覆盖优先、贴图集打平”单独选包；id ≥ 147 的摆放属于户外地图物件，直接排除在室内管线外；解析不了的场景逐个列出，`--strict-props` 时可让构建失败。
2. `tools/rom/extract_overworld_sprites.py`：按家族给方向帧号（左 6–8、右 9–11）；flip 家族镜像生成右侧帧（追加为新的帧文件，客户端不用改）；抽取时用肤色重心自检，左右写反就直接报错。
3. `server`：`walk` step 增加逐跳方向与邻接校验（斜走、跨格、原地跳一律报内容错误），并新增 `face` step（让 NPC 转向玩家或指定方向），对应原版的独立转身动作。
4. 客户端：`npc_face` 消息、`walk` 结束时的定格朝向。
5. 自动化检查（取代人工验收）：`tools/rom/audit_assets.py` 直接从 ROM 重建每个房间的摆放、按名字和 `library.json` 对比，并检查行走图方向；`--self-test` 会合成“正确规则”和“`area[0]` 旧 bug”两份 library，前者必须通过、后者必须报错并点名卧室。剧情 path 的邻接/可走校验则在 `validate-content` 里。

## 复现这些结论

```bash
# 1. 物件档案与坐标（纯 stdlib，不需要 ndspy/apicula）
python3 tools/rom/audit_assets.py --rom .

# 2. 精灵表方向自检
python3 tools/rom/audit_assets.py --rom . --sprites

# 3. 重新抽取（需要 apicula）
python3 tools/rom/extract_unova_indoor.py
python3 tools/rom/build_unova_indoor_worlds.py
python3 tools/rom/build_unova_maps.py
```
